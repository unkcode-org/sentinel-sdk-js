## Current SDK and write contract

`@unkcode/sentinel` 0.4.1 has public `sip_pub_` credentials, normalized HTTPS/loopback Ingest endpoint, OTel logs/traces/metrics, W3C fetch propagation, semantic RUM behind `rum.enabled`, and a single `RumRuntime`. No replay config read, replay policy refresh, replay transport, or recorder exists. `Sentinel.init` starts semantic RUM; `shutdown` owns its lifecycle. Session ID is a crypto-random 32-character lowercase hex ID, restored from `sessionStorage` after reload for <30 minutes of inactivity, and renewed on inactivity. Replay must consume the runtime's current session ID; it must not mint a second session identity or store raw rrweb data. SPA route change emits page_view but is not a hard-document replay page boundary.

Semantic `emit()` creates an event ID and timestamp, then queues the event. The four trigger types are `javascript_error`, `network_error`, `rage_click`, `dead_click`; rage uses pointer attempts/clicks and dead click uses the existing mutation/response window. Hook replay promotion **after** `makeEvent()` succeeds and **before or independently of** semantic queue/flush, passing the same event ID and session ID. Replay failure must not interrupt `emit()`. Do not detect these events again in the recorder. The semantic queue remains authoritative and can drop independently; the replay trigger is the locally emitted semantic event.

Ingest `POST /v1/rum/replay/chunks` accepts one `application/json` v1 envelope with `schema_version`, `session_id`, UUID `replay_id`/`page_id`, page-local `sequence` 0..63, `recorder="rrweb"`, `recorder_version` matching `2.x.y`, RFC3339 `started_at`/`ended_at`, `event_count`, rrweb `events` array, booleans `final`/`truncated`, and optional `{type,event_id}` trigger **only on sequence 0**. Sequence 0 must begin with optional DOMContentLoaded/Load events, then Meta(type 4), FullSnapshot(type 2). Every rrweb event needs a timestamp inside the chunk bounds. Ingest validates one exact Origin and `Bearer sip_pub_...`, credential RUM signal, lifecycle, environment-scoped enabled Core v3 policy, then rechecks policy before Storage write. No browser tenant/application/environment fields are accepted. Request body is identity JSON by default or a gzip-compressed **whole JSON request** using `Content-Encoding: gzip`. Ingest internally gzips the `events` array for Storage. This is not a browser requirement to gzip. Per-request effective limits are at most 256 KiB wire, 1 MiB decoded, 1000 events; cumulative limits at most 64 chunks, 16 pages, 16 MiB decoded event data and 900 seconds. A 202 `{accepted:true,duplicate:boolean}` means Storage persistence, including exact duplicate. 409 conflict, 410 gone, 413 limit, 422 unsupported; 429/503 may return `Retry-After`. Storage derives/fixes the root trigger and limits from the first accepted chunk; later chunks cannot change root identity. Storage has a page-local sequence gap allowance of 8, but the SDK should send sequentially.

**Historical gap, now resolved:** At the first audit, Core v3 policy was only a private Core→Ingest feed and replay OPTIONS supplied no credential-scoped policy. The subsequent authoritative Ingest OpenAPI 0.7.0 added `GET /v1/rum/replay/policy`, which returns the exact public-credential/Origin scoped policy and `fresh_until`. The implemented SDK uses that route; OPTIONS success and POST trial are never treated as enablement proofs. The `Date` response header is not CORS-exposed, leaving the browser clock-skew rollout risk documented in `implementation-summary.md`.

## Proposed dependency and loading

Pin exactly one new direct runtime package: `rrweb@2.1.6`. Use its exported TypeScript types; do not add a direct `@rrweb/types` dependency unless pinned-source implementation proves it necessary. The RUM-7F lockfile already validates the 2.1.6 family (`rrweb`, `rrweb-snapshot`, `@rrweb/types`, `@rrweb/utils`, player packages); lock the recorder's transitives to 2.1.6 and inspect the resolved tree before implementation. Do not add player, packer, plugins, canvas, console or network-body packages to the SDK. Load recorder through an ESM dynamic import only after valid fresh policy and explicit SDK replay opt-in (proposed local `replay.enabled`, default false); keep rrweb out of the initial bundle, and verify `tsup` splitting and the standalone bundle checker do not flatten it into the disabled path. The server policy is mandatory and cannot be overridden by the local flag. No worker in v1 without CSP/copy/teardown measurements.

## State, identity, pages and promotion

State machine: `disabled` → `checking-policy` → `buffering` → `promoting` → `promoted` → `completed`; terminal `disabled-by-policy`, `unsupported`, `privacy-blocked`, `limit-reached`, `upload-failed`, `page-ended`, `destroyed`. Transition to a terminal state stops rrweb and frees buffers/queue as appropriate; semantic RUM continues. Diagnostics, if enabled, use fixed reason codes and existing five-per-reason cap; never IDs, route, URL, selector or content.

Generate replay/page UUID v4 with `crypto.randomUUID()` or crypto-random equivalent; fail closed without secure randomness. The replay belongs to the current semantic session. One document is one page ID. SPA navigation stays within that page. First trigger freezes a single replay ID, trigger type and semantic event ID; subsequent triggers do not create another root or duplicate uploads, and no unsupported trigger metadata is invented. In the same document, continue bounded post-trigger recording. Across hard navigation, discard unpromoted raw prebuffer; a new document gets a new page anchor. **Approved decision:** a promoted replay continues across hard document navigation using only bounded replay/session/trigger identity and accepted-count metadata in `sessionStorage`, never rrweb events, snapshots or chunks. The next document validates TTL, credential/Origin binding, the existing semantic session and fresh policy before recording. Continuation requires at least one valid 202 for the replay's first chunk: before that acknowledgement, the next document starts a fresh prebuffer and needs a new semantic trigger. For subsequent unacknowledged pages, retain only already confirmed chunk/page counts and start another new page under the confirmed replay. Do not claim delivery from unload or mint replacement replay IDs to evade limits.

## Checkpoint buffer and limits

Use rrweb `checkoutEveryNms` and `checkoutEveryNth`, initially aiming <=10 seconds or <=1000 emitted events, confirmed against pinned source and browser tests. `record.takeFullSnapshot(true)` is available but should be a measured fallback, not an unguarded call for every event. An anchor is the Meta+FullSnapshot pair, with optional preceding lifecycle events; a checkpoint group contains its anchor and following increments until the next anchor. Sanitize before admitting any event to memory. Keep only complete groups, plus a bounded in-progress group. On 30-second age, 2 MiB UTF-8 serialized event bytes, or 5000-event pressure, evict oldest **whole** group(s). If the only group exceeds a limit, force a new safe checkpoint; if no valid bounded group remains, stop replay (`limit-reached`) rather than retain orphan mutations. Checkpoint creation itself can be expensive; throttle and bound it, and test adversarial DOM size. A 2 MiB decoded cap is not a JS heap cap: measure object, string and serialized-copy peak in real browsers.

At first trigger, atomically freeze a reconstructable suffix starting at its anchor; include post-trigger events in order. Do not serialize a 16 MiB replay at once. Build and seal small chunks as events arrive, with at most a small number of bounded sealed bodies queued (initial upload concurrency 1 per replay). If queue pressure exceeds the cap, stop recording with a visible local outcome; never drop a middle accepted/pending chunk and continue. Sequence 0 starts with Meta+FullSnapshot and carries the sole trigger. For each chunk, count UTF-8 **whole envelope** bytes and events before sending; leave safety headroom below the effective decoded and wire maxima. A single oversized snapshot cannot be split; stop and report locally. Subsequent chunks may contain increments/checkouts, but never precede their anchor. Track aggregate accepted plus pending decoded event bytes, chunks, page count and duration against `min(server policy, local safety cap)`; stop before knowingly exceeding. `final`/`truncated` are frozen when sealing and cannot be changed on retry; an already sent nonfinal chunk cannot retroactively become final. Storage remains authoritative.

Use identity JSON requests first: the SDK already has browser `fetch`, and the policy floor allows requests >=1024 bytes. This avoids depending on `CompressionStream`, browser gzip differences, and a second byte copy. If measured bandwidth later requires gzip, add it as a separate verified decision: gzip the **entire frozen JSON envelope**, set `Content-Encoding:gzip`, enforce both wire and decoded sizes, and test browser support. A first FullSnapshot too large for effective identity request size is a local stop, not a license to bypass policy. Freeze the exact serialized body and metadata once; retries reuse the same bytes, URL, IDs, sequence and headers.

Send one chunk at a time, with 202 as the only persistence acknowledgement. Bound retries (proposal: initial plus two retries), jittered exponential backoff, capped valid `Retry-After`, and a total elapsed deadline; never retry 400/401/403/409/410/413/415/422. Retry 429, 500, 503 and transport timeout only while policy is fresh and page/session alive. A 401/403 triggers policy invalidation and recorder stop. Abort on shutdown/pagehide; an unacknowledged chunk remains unconfirmed. Do not use `sendBeacon`; it cannot provide the required 202 response and Bearer header. Do not rely on unload. `visibilitychange` may seal a small chunk while the page is alive, but hidden state is not a persistence guarantee. Replay upload is isolated from semantic RUM and OTel transport, including fetch instrumentation exclusion for the replay URL.

## Policy refresh and performance

The new browser policy mechanism should own one refresh timer, fresh-until deadline and `AbortController`; do not add a second poller. On enabled→disabled, malformed/stale/unsupported, or credential/Origin rejection: promptly stop recorder and pending uploads, discard unpromoted data, retain already accepted chunks, and leave semantic RUM running. Apply lowered limits immediately; if already over a new limit, stop rather than sending more. Disabled→enabled starts a fresh buffer and anchor only after fresh policy in the current page, never backfills earlier activity. Session rollover ends the old replay before using the new semantic session ID. Instrument separately in tests: disabled startup and bundle bytes; enabled import/startup; mutation-heavy and large DOM long tasks; per-event sanitization; checkout cost; promotion latency; queue/serialization and bandwidth; peak heap with object+string+body copies. No production performance claim follows from the decoded byte cap alone.
