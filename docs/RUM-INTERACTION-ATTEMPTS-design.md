# RUM-TARGET-1.1 — interaction attempts under one rage-click semantic

Status: **interaction/privacy contract approved for SDK-only attempt capture; target-state wire fields deferred**
Audit: 2026-09-29. This supersedes the earlier proposal for a separate `repeated_interaction` event. No new event type is proposed.

## Current behavior and observed browser events

`RumRuntime` listens for `click` at document capture. It emits a `click`, sends the same resolved element/target to rage detection, and starts a dead-click timer only for eligible buttons. Rage uses three clicks against the same DOM element within 1,000 ms and normalized spatial radius 0.04, a 16-sample history, and a 1,000 ms emission suppression. Its wire detail is `click_count` and `duration_ms`. Dead-click remains a separate 700 ms response test. The SDK has no pointer listeners.

A real-pointer Playwright fixture pressed enabled and disabled buttons with direct text or a span three times. Chromium, Firefox, and WebKit all delivered document-capture `pointerdown`, `mousedown`, `pointerup`, `mouseup`, `click` for enabled buttons; native disabled buttons delivered `pointerdown`, `pointerup` only. Enabled fixtures emitted three clicks, one rage click, and three dead clicks with `text: Confirmar compra`; disabled fixtures emitted nothing. This is desktop mouse evidence only. Touch, pointer capture, custom controls, and non-interactive elements still require the matrix below.

TARGET-1 permits bounded text on eligible small interactive controls, including a disabled native button; `disabled` currently affects only dead-click eligibility. Its bounds remain eight ancestors, twelve direct children, twenty inspected nodes, 160 source characters, and 80 UTF-8 output bytes. Arbitrary div/span/page text is not approved. Ingest's event and target objects are closed; Storage/Query/frontend understand `rage_click` and its current target/detail fields.

## Approved direction and proposed interpretation

Use one event type, `rage_click`, to mean **multiple rapid, spatially close interaction attempts against the same logical target**. One qualifying native browser click counts as one attempt. One qualifying completed pointer pair without a correlated native click also counts as one attempt. Never count the pair and its click twice. `click` emission and dead-click behavior stay as they are; no click is fabricated for a disabled or generic element. `rage_click` can contain a mixture of clicked and non-clicked attempts.

The existing `data.click_count` wire name is historical. For the broadened event it would contain the number of qualifying attempts in the cluster, including ones with no click. Keeping the field is mechanically compatible with Ingest/Storage/Query validation and old records; documentation and UI must call it **attempts**, and must disclose the legacy wire name. Renaming/adding an `attempt_count` field would itself require end-to-end schema work and is not proposed for this slice. Old records have click-only attempts; new records may include non-click attempts. Both remain valid rage observations, but trend comparisons across the SDK rollout have a coverage break. Without a source/version field, old events cannot be retroactively classified by attempt source.

## Bounded attempt state machine

The existing rage thresholds remain unchanged. The SDK uses a 10 CSS px movement limit, a 750 ms maximum press, and a 32 ms pointer-up-to-click correlation window. In repeated runs of 20 real mouse and 20 touch taps per engine, measured maximum gaps were 2.3 ms (Chromium), 10 ms (Firefox), and 2 ms (WebKit). The 32 ms window covers those measurements with margin while letting disabled/non-click rage settle promptly. The fixture asserts both input modes stay below this window; future browser regressions must fail before increasing it.

| State | Input and rule | Result |
| --- | --- | --- |
| Idle | Trusted, primary `pointerdown`, `button === 0`, finite coordinates, eligible target/route. | Store `pointerId`, pointer type, down time/position, logical DOM element, and cancel flags in memory only. No click or rage sample yet. |
| Pressing | Matching `pointerup` by `pointerId`; same logical element, same route, connected element, within draft 10 CSS px movement and draft 750 ms press duration, with no scroll/drag/cancel. | One provisional attempt at the release time/position. |
| Pressing | `pointercancel`, second active touch pointer, scroll/touch gesture, meaningful movement, long press, route change, removed/replaced element, or shutdown. | Discard. Do not synthesize browser behavior. |
| Provisional | A correlated trusted native `click` arrives within 32 ms after release. Require same logical element and nearby position; use pointer identity on click only where available/reliable. | Consume the provisional pair. The existing click handler emits its normal click and contributes exactly one click-derived rage sample at the click's native time/position. Dead-click candidacy remains the existing click-only rule. |
| Provisional | Correlation window ends with no click. | Convert to one non-click rage sample at the release time/position. Emit no `click` and no `dead_click`. |
| Rage history | Three settled attempts with one stable element identity, all within the existing 1,000 ms sample-time window and normalized radius <= 0.04. | Emit one `rage_click` with existing target/position/data shape and existing 1,000 ms suppression. |

A click with no pointer pair (including keyboard activation) continues through the existing click path and counts once for rage, as today. An untrusted/synthetic click continues under the existing `onClick` policy; it must never be correlated to a trusted pointer pair or cause duplicate pointer-derived counting. Pointer attempts themselves require trusted events. If click matching is ambiguous, discard the provisional sample from non-click classification to avoid duplicate counting; preserve the native click path. A click arriving unusually late after 32 ms is a browser-calibration risk to test, not a reason to invent a click.

The click-only path must retain its current immediate third-click rage behavior. To handle mixed sequences, keep provisional release timestamps until settled, and keep a bounded settled history long enough to examine the existing 1,000 ms sample-time window after the correlation delay. Do not widen the rage **sample-time** or spatial threshold. On a late finalization, evaluate the original sample timestamps, not wall-clock arrival order. Preserve existing DOM-element grouping; do not group by changing text, test ID, CSS path, or viewport position alone. A rage event from a mixed/non-click cluster may be emitted after its final pointer pair while click correlation expires.

Proposed memory caps: at most eight active pointer IDs, sixteen provisional pairs, and sixteen settled samples; evict oldest on overflow. Reuse the existing one-second rage suppression and 16-sample cap where possible. Do constant work for moves and one bounded ancestor/target resolution on down/up; listeners must be passive where compatible, must not call `preventDefault()` or take pointer capture, and must be removed on shutdown. Performance acceptance must measure high-rate move overhead and ensure click latency does not regress.

## Logical target and privacy

**Known controls:** Native button/link and supported interactive roles resolve through the existing bounded TARGET-1 path. A span/SVG child can resolve to its parent control within the existing ancestor limit. Apply the current `aria-label` precedence, text bounds/sanitizer, and private/sensitive/hidden/inert/editable exclusions. Native disabled is not itself a privacy exclusion. Read only the control's approved text; do not deepen traversal. `aria-disabled="true"` is author-declared state and does not suppress browser click delivery by itself.

**Generic targets:** The pointer path makes a complete eight-element ancestor safety walk. It then resolves within the first four elements from the event target: prefer the nearest own safe test ID, otherwise the nearest element outside a fixed presentation tag set (`span`, formatting tags, `svg`, `g`, `path`, `use`), otherwise the original element. This maps `div > span` and `div > svg > path` to their nearby div without climbing to a broad page container. Require the same connected resolved element and unchanged direct parent/source parent from down to up; group by that element identity. Exclude document/html/body, form inputs and their labels, editable regions, hidden/inert regions, and private/sensitive ancestry. If the bounded walk cannot establish eligibility, omit the pointer-derived sample. Do not infer actionability from CSS/cursor, geometry, nearby text, `alt`, `title`, `src`, or arbitrary attributes. Generic wire target is safe tag and its **own** safe role/test ID; no CSS selector or arbitrary ancestor test-ID fallback. This pointer collection surface is approved for this SDK slice.

**Generic text:** No `label` or `text` for unroled non-interactive targets in this proposal, even when a div/span visibly contains words. TARGET-1 approval does not cover arbitrary page text. Any opt-in generic text requires a separate explicit privacy amendment with fixed eligibility, the current or tighter 8/12/20/160/80 budgets and sanitizer, and private/sensitive/hidden exclusions. A generic rage event with tag, normalized position, and count remains useful without page text. For the new pointer-derived path, omit the entire sample in private/sensitive regions; retain existing click-family behavior unchanged.

**Target state (separate additive contract):** An optional boolean `target.disabled` should be present as `true` or `false` for an inspected native button: `true` means the native disabled state was set at the attempt, `false` means it was not. Omit it for inapplicable targets and historical rows, so absence means unknown/inapplicable rather than enabled. A separate optional `target.aria_disabled` should reflect only the target's own exact `aria-disabled="true"` or `"false"` value; omit it when the attribute is absent or malformed. Native and ARIA state are different facts and should remain separate. Do not read reasons, user values, or associated form content. Decide sampling at completed attempt and fail closed on mid-press state changes. These fields require closed-schema/validation/storage/query/frontend changes and are **not implemented**. Without them, a `rage_click` on a button cannot reliably prove why native clicks were absent.

## Browser test matrix and TDD decomposition

1. Preserve the existing enabled/disabled four-fixture real-pointer baseline in Chromium, Firefox, and WebKit. Add failing tests for three disabled native presses yielding one rage event with bounded target text and zero click/dead-click events; enabled presses must retain three clicks, one rage, and their current dead-click behavior. Include aria-disabled role controls and unroled div/span/img with no generic text.
2. Pairing tests: pointer IDs, different down/up targets, nested child and SVG, removal/replacement/reparenting between events, shadow-root retargeting, pointer capture, non-primary buttons, pen, and concurrent multi-touch. Require continuity or omit on ambiguity.
3. Gesture rejection: pointercancel, drag across and just below the draft movement boundary, touch scroll, document scroll, long press across the draft duration boundary, release outside, route change, and shutdown. Verify no false rage from those sequences.
4. Correlation/dedup tests: immediate/delayed click, click without pair (keyboard), synthetic/untrusted events, paired enabled click, no-click pair, mixed sequence, and late click after timeout. Assert one rage sample per physical action and unchanged click/dead-click payloads. Calibrate correlation duration in all three engines, including touch where automation supports it.
5. Boundary/privacy tests: current 1,000 ms rage window, normalized 0.04 radius, 16-sample history, suppression behavior, large/deep DOM, private ancestors/descendants, hidden/inert/editable/form regions, unsafe text, and complete serialized POST body. No unrestricted DOM text reads.
6. Performance/lifecycle tests: high-rate moves, pointer storms and cap eviction, listener ownership/cleanup, bounded queue, bundle budget, and no observable browser behavior change. Run full SDK verification after implementation approval.

## Compatibility, boundaries, and rollout

**SDK-only mechanics under the approved interaction/privacy decision:** pointer pairing, click correlation, and emitting the existing `rage_click` shape are implemented in this repository while preserving `click` and `dead_click`. No new event type, protobuf enum, database event table, or ingest event union is necessary while `click_count` remains the legacy wire field. Frontend wording should change from “clicks” to “attempts” in a later coordinated slice; this task does not change that repository.

**End-to-end Target contract change:** `disabled`/`aria_disabled` (or any other new target property) requires Storage protobuf/domain/ClickHouse read/write/validation, Ingest decoder/OpenAPI/mapping/validation, Query DTO/OpenAPI/mapping/validation, frontend generated types/schema/rendering, and SDK emission. Deploy Storage support first, then Query and Ingest compatibility, then frontend display, then SDK emission last. Strict Ingest decoding would reject a new target key from an early SDK and could reject its whole batch. Historical target rows have absent/unknown state.

**Aggregation:** Storage/Query `rage_click_count` is a physical count of events with `event_type = rage_click`; `has_rage_clicks` and event-type filters remain mechanically valid. `click_count` remains a bounded integer detail, now counting attempts by contract despite its legacy name. Old and new rage counts answer the same broad question but have different detection coverage. Product charts, filters, and timeline text must disclose the rollout boundary or SDK version when comparing periods; do not silently describe all observations as browser clicks. `dead_click_count` and click event counts remain unchanged. No new aggregation column is required for the core attempt-only change.

## Human gate

The user approved the single-event direction, pointer attempt architecture, generic-target privacy boundary, and revised `click_count` meaning for this SDK slice. The 32 ms correlation value is selected from the three-browser mouse/touch fixture. Optional target-state fields remain outside this approval and require their own end-to-end contract implementation. No deploy.
